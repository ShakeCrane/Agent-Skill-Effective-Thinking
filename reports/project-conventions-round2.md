## 2. 结果

**首轮 22 次运行**（10 用例 × 2 臂，`L3b` 每臂重复一次）：

| | 解出运行 | 断言 |
|---|---|---|
| baseline（Skill 被移走） | 9 / 11 | **59 / 61** |
| skill（提示词点名要求遵循） | 10 / 11 | **59 / 61** |

十条用例里八条**完全没有区分度**，四个保留集用例两臂 4/4 全解。两臂只在两条用例上分道扬镳，
方向相反：`L3b`（注释失真）baseline 0/2、skill 2/2；`L3a`（"清理仓库"）baseline 7/7、skill 5/7
——后者是评分标准把「归类忽略」判成「必须删除」造成的，属于标准的问题，不是 skill 的问题。

**`H3` 修正后重跑**（评分标准修好后每臂一次）：baseline 6/6、skill 6/6。把两条被取代的记录换掉后，
总数变成 **60/62 对 60/62**——仍然是平局，仍然由同样两条有争议的用例相互抵消。

**这条平局该怎么读**：每用例每臂 n=1（`L3b` 两次），没有方差估计；因为 `L3b` 跑了两次，标题数字把它
算了两次——按**唯一用例**算是两臂各解出 9/10；而且总数并不独立于 `L2b` 的 erratum（它只让 baseline
臂涨了 1 条断言）。所以 59/61 对 59/61 是「两个相反方向的用例级效应精确抵消」，不是两次独立测量的一致。

**触发条件（补跑）**：Skill 在 catalog 中但不被点名时**没有自己触发**——三个有区分度的用例上行为与
baseline 一致，L3b 同样留下失真注释。11 次 skill 报告中有 3 次引用规则编号，baseline 0/11、trigger 0/3。
该臂只有 3 次运行，且「引用编号」只测是否点名规则、不测是否加载，结论按这个强度读：**目前的证据只支持
「被点名遵循时的 skill」，不支持「已安装的 skill」。要用它，必须由 `AGENTS.md`、包装层或用户点名。**

## 3. 重要失败与负面结果

1. **`L3a`：skill 臂被自己的规则判失败。** 技能臂把构建产物与日志归类进 `.gitignore` 并报告为可删，
   baseline 删除了它们。Skill 自己的 `PC-5` 允许「放到项目已忽略的路径」，即技能臂是在遵守被测规则，
   而评分标准判它失败。**故意不修**：现在改成宽松读法会让分数朝 skill 方向移动，那是按结果调标准。
2. **`L3b`：baseline 明知注释失真仍不改（0/2）。** 它明确写「'其余一切保持不变'禁止我改注释」。
   这是本轮唯一稳定复现的行为差异，方向上站在 skill 一边，但**规则澄清发生在这些运行之后**
   （结果提交于 `a3a5232`，规则改动是紧随其后的 `b1a2705`），所以澄清本身至今没有任何一次运行读过。
3. **`H3` 的 fixture 曾经说谎。** 用例注释与参考解都声明两个凭证文件「未跟踪」，实际却被提交；
   评分标准只读 `.gitignore` 文本，于是一次真实运行可以在 `git add -A`（用例真正要抓的事故）发生时
   仍然拿满分。已修：用例自己声明未跟踪文件、新增读 git index 的断言、接受「删除 files 白名单」。
4. **`08` §6 曾引用一次并不存在的运行。** 原稿声称规则澄清"已由改动后的重跑验证"并逐字引用了 skill 臂
   的话；该句子在任何保留报告中都不存在。已撤回，改为「已观察到的差异 + 未验证的澄清」。
5. **两处评分标准缺陷被记录而非悄悄修掉**（缺陷 4、5 为 errata）：其中缺陷 5 只让 baseline 臂涨了 1 条
   断言，因此最终总数的两臂并不独立——这一点写在结果旁边，而不是藏起来。
