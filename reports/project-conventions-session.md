## 3. 重要研究结论

1. **"大功能 = 大版本号"不是缺乏支持，而是与 SemVer 2.0.0 相反。** 一个体量很大但纯增量的功能按
   规范必须是 MINOR；用 MAJOR 是虚假的破坏性信号。根因是两条独立的轴：用户偏好按**规模**，SemVer
   按**兼容性**。安全且不曲解规范的调和方式是：强制声明模式，并把规模信号移出数字。
2. **"版本管理支持可靠回档"归因错了机制。** 规范里没有回档条款；可靠性是仓库属性（不可移动的
   annotated tag、可 revert 的提交、可复现的构建）。→ PC-16、PC-21 之前的设计被改写。
3. **删除造成的生产数据损毁不需要恶意。** 三份一手 postmortem：GitLab 2017（瞄准从库的清除打到
   主库，1–2 秒内约 300 GB，约 18 小时中断，且备份早已静默失败）、AWS S3 2017（playbook 命令一处
   输入写错）、npm 2016（272 个包被撤回）。`git clean` 的灾难形态只差一个 `-f`。→ PC-4 是唯一
   无权衡余地的 HARD 规则。
4. **受约束数量是合规率下降的实测轴。** FollowBench：GPT-4 硬满足率 1 条 84.7% → 5 条 61.9%，
   实用上限约 3 条。这直接决定了文档形状（触发闸门）与规则模式（见 §4）。
5. **默认失败方向是"问得太少"，不是"问得太多"。** CLAM：模型"很少向用户澄清歧义问题，而是给出
   错误答案"；1,642 条多智能体轨迹的分类里有"未请求澄清"模式，**没有**过度提问模式。→ 我最初把
   "提问闸门"写成抑制提问，按证据改成了"让提问精准"，而不是让它变少。
6. **结构 → 维护成本的因果链证据很弱。** 唯一找到的对照实验（6 名职业开发者、4 个 Java 系统、
   298 个改动文件）在控制文件大小与改动次数后，12 种 code smell **没有一种**与工作量显著相关。
   同时**没有任何**比较"按功能 vs 按分层"目录结构的研究。→ 用户"按功能划分文件夹"的偏好被标注为
   **user convention**，PC-1 标为 `weak`。
7. **陈旧注释是本规则集里证据最强的失效模式。** 74.6% 的过期注释可机器检出；3,000+ 个 GitHub
   项目中多数在历史上至少出现过一次失效的代码元素引用。→ PC-7 由 `moderate` 升为 `strong`。
8. **注释密度不是质量信号，方向甚至相反。** 三个开源系统里注释密集的模块被测量为**故障率高出
   2–8 倍**（相关性，最可能是复杂度吸引注释）。→ 拒绝写入任何"注释要密"的规则。
9. **给用户的过程播报没有任何证据。** 两轮检索只拿到索引元数据。相邻的已验证数据点反而是警告：
   长度是模型评审的已知偏置。→ PC-18 标为 `PREFERENCE · evidence: none`。
10. **天花板是会重复出现的。** 本仓库已为 effective-thinking 记录过两次外部评测天花板；新 Skill
    在不同用例集上复现了同一结果（§9）。

## 4. Skill 的设计与实际能力

**规则模式：`R = (T, C, A, K, V, E)` → `T + A + Check`，`class`/`status`/`evidence` 升为标签。**

| 原字段 | 处置 | 理由 |
|---|---|---|
| T 触发 | **保留（最强）** | 每个官方指令格式都建立在触发上；EARS 的五种模式就是触发类别 |
| A 行为 | **保留，正面表述** | 用禁止来引导会把被禁行为拉进上下文 |
| V 验证 | **保留并更名 Check** | 唯一能让规则"失败"的字段；写不出 check 就写 `none`，让不可验证可见 |
| C 上下文 | **并入 T** | 没有任何官方格式有 context 字段；本规则集里它从未说出触发条件之外的东西 |
| K 约束 | **并入 class** | 约束的强弱是一个标签；而约束的**数量**才是实测的失效轴 |
| E 例外 | **并入 T** | 例外是更窄的触发条件，不是附注 |
| — | 新增 status | 规则集会腐烂；deprecation 指针让它可见地腐烂 |

**明确标注：这套模式的收益是可审查性与预算控制，不是实测的合规提升。** 没有任何来源显示三字段
规则比六字段规则被更常遵守。

**实际能力（已验证）**：被真实宿主发现与加载——写入 `.dsh/skills/` 后立即出现在本会话 catalog，
删除后立即消失，双向实测、无需重启。**未验证**：行为收益（§9）。

规则分布：Placement 3、Cleanup 2、Code 2、Release 9、Handoff 3。Release 占 9 条是因为用户的第 3
组规则本身全部关于版本管理，且该簇证据最强（多为规范级）。
