## D0. Executive summary

- **The number of simultaneously-active constraints has a measured, steep ceiling.** FollowBench (ACL 2024) adds one constraint at a time: GPT-4-Preview-1106 hard-satisfaction rate falls **84.7 % → 61.9 %** from 1 to 5 constraints; the paper states the "instruction-following upper bound" is "**approximately 3 constraints**" for GPT-4/GPT-3.5 and "about 2" for open models [S13].
- **Instruction compliance also decays with conversation length, not just count**: "significant instruction drift within eight rounds of conversations", attributed to attention decay [S16]; Multi-IF shows o1-preview falling **0.877 → 0.707** by turn 3 [S15].
- **The official Skill format already encodes the fix: progressive disclosure.** Only `name`+`description` (~100 tokens/skill) are always loaded; the body is loaded on trigger; further files cost "None until accessed" [S1]. The always-loaded tier is the only tier with a hard, measured budget.
- **Every official format has a trigger field and none has a "context" field**: `description` [S1,S5,S9], Cursor's three-way `alwaysApply`/`description`/`globs` table [S7], Copilot `applyTo` globs [S8], Claude Code `paths` globs [S11], EARS' `When`/`While`/`Where`/`If` keywords [S24].
- **Body budgets are explicit and small**: "Keep SKILL.md body under 500 lines" [S2], Level-2 "Under 5k tokens" [S1], "target under 200 lines per CLAUDE.md file. Longer files consume more context and reduce adherence" [S11]. Auto-memory hard-loads only "the first 200 lines of MEMORY.md, or the first 25KB" [S11].
- **The observed production corpus is ~10× under the ceiling**: 25 SKILL.md files, median **71** lines, max **140**, **zero** over 500; detail is disclosed into 22 sibling reference files (max 207 lines) [S47].
- **Position matters as much as content**: performance is "highest when relevant information occurs at the beginning or end" and degrades in the middle [S18]; permuting premise order costs "over 30%" [S19]; pure formatting changes move accuracy "up to 76 accuracy points" [S20].
- **Conflicts are resolved by an authority chain, not by the model reasoning about them.** Official chains exist (OpenAI Model Spec Platform>Developer>User [S23]; Cursor Team>Project>User [S7]; Copilot personal>repo>org [S8]; AGENTS.md nearest-file-wins [S6]) — and Anthropic concedes that without one, "if two rules contradict each other, Claude may pick one arbitrarily" [S11].
- **Verification clauses earn their keep only when a real check exists.** Prose is not enforcement — Claude Code: "Claude treats them as context, not enforced configuration. To block an action regardless of what Claude decides, use a PreToolUse hook instead" [S11] — but where a deterministic validator exists, the validator→fix→repeat loop "greatly improves output quality" and gives "objective verification" [S2], process supervision beats outcome supervision [S38], and behavioural test matrices find ~3× more bugs [S40]. A "check your work" instruction is the soft case; intrinsic self-correction without external feedback *degrades* performance [S37].
- **Self-modification is where the evidence is weakest and the failure modes clearest**: prompt optimisers work on a metric (APE beats human instructions on 19/24 tasks [S32]; APO +31 % [S33]; DSPy compiles to "maximize a given metric" [S34]) but intrinsic self-correction *without external feedback* fails and "at times, their performance even degrades" [S37].
- **Mature rule systems all separate severity, lifecycle status and removal policy** — ESLint `off`/`warn`/`error` [S25], rule metadata (recommended/fixable/frozen/deprecated) [S27], machine-readable dates where `availableUntil: null` means "no longer changed but **kept available**" [S49], a written removal gate ("Rules will never be removed from ESLint unless… replaced by another core rule / a plugin exists with a functionally equivalent rule") [S26], and a graduation bar before freeze ("catches **80 % or more of expected violations**") [S50]. Policy-as-code adds the missing piece prose rules lack: ambiguity is an **error**, not a guess [S28].
- **Recommendation on R = (T, C, A, K, V, E): keep T, A, V; convert E into T; drop C; demote K to a severity tag.** The evidence supports three per-rule fields plus two document-level fields (severity, status), not six. Full reasoning and token budget in D10.

## D1. Official Skill / instruction-file formats (quoted guidance)

**S1 — Anthropic Agent Skills overview** (`official docs`). Three load levels: metadata always loaded at "**~100 tokens per Skill**"; instructions "**When Skill is triggered**", "**Under 5k tokens**"; resources "**None until accessed**" — "Scripts run through bash, and only their output enters context". Frontmatter: `name` "Maximum 64 characters… only lowercase letters, numbers, and hyphens… Cannot contain reserved words: 'anthropic', 'claude'"; `description` "Maximum 1024 characters". "The `description` is what Claude matches your request against when determining whether to trigger the Skill, so it must say both what the Skill does and when to use it." On load: "When you request something that matches a Skill's description, Claude reads SKILL.md from the filesystem using bash."

**S2 — Skill authoring best practices** (`official docs`). "**Keep SKILL.md body under 500 lines for optimal performance**"; "Split content into separate files when approaching this limit". Naming: "Consider using **gerund form** (verb + -ing)". Descriptions must be "**Always write in third person**" — "The description is injected into the system prompt, and inconsistent point-of-view can cause discovery problems". "**Keep references one level deep from SKILL.md**" (deeper nesting causes partial reads). "For reference files longer than 100 lines, include a table of contents at the top." Splitting: "When the `SKILL.md`file becomes unwieldy, split its content into separate files… If certain contexts are mutually exclusive or rarely used together, keeping the paths separate will reduce the token usage." Conciseness: "**Default assumption: Claude is already very smart**… Only add context Claude doesn't already have", with a worked pair: concise ≈50 tokens vs verbose ≈150 tokens. Freedom: high/medium/low, chosen by fragility ("Narrow bridge with cliffs on both sides… Open field with no hazards"). Evaluation: "**Create evaluations BEFORE writing extensive documentation**", "Build three scenarios", "At least three evaluations created". Anti-patterns: "Avoid offering too many options", "Avoid time-sensitive information". Maintenance: "Use **old patterns** section" for deprecated material, tucked into `<details>`.

**S3 — Anthropic engineering, "Equipping agents for the real world with Agent Skills"** (`official docs`/vendor engineering, 2025-10-16). "Progressive disclosure is the core design principle that makes Agent Skills flexible and scalable." "This means that the amount of context that can be bundled into a skill is **effectively unbounded**." Authoring loop: "Start with evaluation… Structure for scale… Think from Claude's perspective… Iterate with Claude". Forward-looking (relevant to D5): "we hope to enable agents to create, edit, and evaluate Skills on their own".

**S4 — agentskills.io** (`standard/spec`). Skills "load skills through **progressive disclosure**, in three stages: **Discovery**… **Activation**… **Execution**". Folder layout `SKILL.md` + optional `scripts/`, `references/`, `assets/`.

**S5 — Claude Code skills** (`official docs`). "Put the key use case first: the combined `description` and `when_to_use` text is **truncated at 1,536 characters** in the skill listing". Body discipline: "Keep the body itself concise. Once a skill loads, its content stays in context across turns, so **every line is a recurring token cost**. State what to do rather than narrating how or why." Invocation control: `disable-model-invocation: true` prevents autonomous loading; `paths` globs "limit when this skill is activated". Outside Claude Code only six spec fields survive (`allowed-tools, compatibility, description, license, metadata, name`); anything else fails packaging with a hard error.

**S6 — AGENTS.md** (`standard/spec` convention, now stewarded by the Agentic AI Foundation). "Are there required fields? **No. AGENTS.md is just standard Markdown.** Use any headings you like." Conflict rule: "**The closest AGENTS.md to the edited file wins; explicit user chat prompts override everything.**" Scale: "at time of writing the main OpenAI repo has 88 AGENTS.md files"; "60k+ examples on GitHub". Maintenance stance: "**Treat AGENTS.md as living documentation.**" Verification: "Will the agent run testing commands found in AGENTS.md automatically? Yes—if you list them."

**S7 — Cursor rules** (`official docs`). Trigger is a 3-field table: `alwaysApply: true` → "Always included"; `globs` present → "Auto-attached when a matching file is in context"; `description` present → "Agent reads the description and pulls the rule in when relevant"; neither → manual `@`-mention only. Budget: "**Keep rules under 500 lines**", "Split large rules into multiple, composable rules". Growth policy: "**Start simple. Add rules only when you notice Agent making the same mistake repeatedly.** Don't over-optimize before you understand your patterns." Anti-patterns: "**Copying entire style guides: Use a linter instead.** Agent already knows common style conventions"; "**Documenting every possible command**"; "**Adding instructions for edge cases that rarely apply**"; "**Duplicating what's already in your codebase**: Point to canonical examples instead of copying code". Staleness: "Reference files instead of copying their contents—this keeps rules short and **prevents them from becoming stale** as code changes."

**S8 — GitHub Copilot repository custom instructions** (`official docs`). Three mechanisms: repo-wide `.github/copilot-instructions.md`; path-specific `NAME.instructions.md` with `applyTo` globs (plus `excludeAgent: "code-review" | "cloud-agent"`); and "Agent instructions" via AGENTS.md — "the nearest `AGENTS.md` file in the directory tree will take precedence". Priority: "**Personal instructions take the highest priority. Repository instructions come next, and then organization instructions are prioritized last. However, all sets of relevant instructions are provided to Copilot.**" Guidance: "**Whenever possible, try to avoid providing conflicting sets of instructions.**" The official generation prompt bounds size: "**Instructions must be no longer than 2 pages. Instructions must not be task specific.**"

**S9 — `@deepseek-ai/dsh-skill-filesystem` README** (`local-file`, host's own provider contract). Frontmatter: "required `name` and `description`, plus optional `whenToUse`, `metadata`, `disable-model-invocation`, and `user-invocable`"; "`name` must be kebab-case". Discovery: directory bundle `<name>/SKILL.md` or flat `<name>.md`; "**nested `**/SKILL.md` files are deliberately not discovered**". Priority ranks 100 → 600 (project `.dsh/skills` → project `.agents/skills` → custom → user dsh → user agents → bundled). Lifecycles: "The catalog and the body have separate lifecycles… editing a skill body needs no versioning or cache invalidation", but "**No body revision protocol** — a loaded body is ordinary retained tool history". Silent failure: "A file without valid frontmatter, an invalid name, or an invalid invocation value is skipped with a warning, so **the model catalog receives no per-skill diagnostic and cannot distinguish an absent skill from an invalid one**."

**Cross-format synthesis (my inference).** Four independent vendors converge on the same three-part architecture: (1) an always-loaded trigger string with a hard character cap; (2) small, scoped bodies; (3) on-demand reference behind one hop. The disagreements are instructive: Cursor and Copilot allow path-glob triggering that Anthropic's format does not, and only dsh and Claude Code are documented as silently dropping malformed files.

## D2. Instruction-following vs number of instructions (measured)

**S12 — IFEval, Zhou et al. 2023** (`preprint (arXiv)`, arXiv:2311.07911 — id verified). "We identified 25 types of those verifiable instructions and constructed around 500 prompts, with each prompt containing one or more verifiable instructions." Reported overall: GPT-4 prompt-level strict 76.89 %, instruction-level strict 83.57 %; PaLM 2 S 43.07 % / 55.76 %. The paper reports totals, not a per-count curve.

**S13 — FollowBench, Jiang et al., ACL 2024** (`peer-reviewed`, arXiv:2310.20410). **This is the key measured curve.** Method: "we introduce a Multi-level mechanism that incrementally adds a single constraint to the initial instruction at each increased level", producing levels L1–L5 (820 instructions); metric **Hard Satisfaction Rate (HSR)** = fraction of instructions where *all* constraints are met.

| model | L1 | L2 | L3 | L4 | L5 | CSL (consecutive levels satisfied) |
|---|---|---|---|---|---|---|
| GPT-4-Preview-1106 | 84.7 | 75.6 | 70.8 | 73.9 | 61.9 | 3.3 |
| GPT-3.5-Turbo-1106 | 80.3 | 68.0 | 68.6 | 61.1 | 53.2 | 2.9 |
| Qwen-Chat-72B | 73.8 | 63.3 | 54.3 | 45.2 | 39.9 | 2.4 |
| LLaMA2-Chat-70B | 59.9 | 53.3 | 46.0 | 40.2 | 37.9 | 2.1 |
| Vicuna-13B-V1.5 | 71.2 | 60.2 | 49.6 | 40.6 | 34.0 | 2.1 |
| ChatGLM3-6B | 60.9 | 46.6 | 36.7 | 27.8 | 21.4 | 1.6 |

Paper's own reading: "(1) the performance of all tested models **declines substantially with an increase in difficulty level** (the number of constraints in an instruction)"; "the instruction-following **upper bound for GPT-4 and GPT-3.5 is approximately 3 constraints** (level 3)… open-source models typically have an upper limit of about 2 constraints"; "**even the most sophisticated models are limited to following instructions with about three constraints**". Category asymmetry: "most models demonstrated commendable proficiency under the **Style** constraint", while "the **Example** and **Mixed** constraints posed a challenge to most models". Counter-intuitive sub-finding: better models can show *lower* "failure consistency" across levels.

**S14 — InFoBench** (`preprint (arXiv)`, arXiv:2401.03601). Introduces "the Decomposed Requirements Following Ratio (DRFR)… breaks down complex instructions into simpler criteria"; 500 instructions, 2,250 decomposed questions. Reports models' weaknesses "**particularly in complex instruction-following**".

**S15 — Multi-IF** (`preprint (arXiv)`, arXiv:2410.15553). "**All the models tested showed a higher rate of failure in executing instructions correctly with each additional turn.** For example, o1-preview drops from **0.877 at the first turn to 0.707 at the third turn**."

**S16 — Instruction (in)stability / drift, Li et al., COLM 2024** (`peer-reviewed`, arXiv:2402.10962). "An implicit assumption in the use of system prompts is that they will be stable… Testing popular models like LLaMA2-chat-70B and GPT-3.5, we reveal a **significant instruction drift within eight rounds of conversations**. An empirical and theoretical analysis… suggests the transformer attention mechanism plays a role, due to **attention decay over long exchanges**."

**S17 — ComplexBench, NeurIPS 2024 D&B** (`peer-reviewed`, arXiv:2407.03978). "ComplexBench identifies **significant deficiencies in existing LLMs when dealing with complex instructions with multiple constraints composition**."

**On the phrase "instruction-following ceiling".** I found **no peer-reviewed or official source that uses this term as a defined quantity**, and no published curve of *system-prompt length* vs compliance. The nearest legitimate quantities are FollowBench's CSL (~3 constraints, per instruction) [S13] and Anthropic's official line-count targets (500 lines for SKILL.md [S2]; 200 lines for CLAUDE.md [S11]). One unverified practitioner page (claude-wiki.com) claims a "~60–100 lines before degradation begins" figure; **I did not fetch it, it shows no provenance, and I treat the number as UNVERIFIED — do not use it.** See D13.

## D3. Position, structure, formatting effects

- **S18 — Lost in the Middle, Liu et al., TACL 2023** (`peer-reviewed`, arXiv:2307.03172). "performance can degrade significantly when changing the position of relevant information… performance is often **highest when relevant information occurs at the beginning or end** of the input context, and **significantly degrades when models must access relevant information in the middle** of long contexts, even for explicitly long-context models."
- **S19 — Premise Order Matters, ICML 2024** (`peer-reviewed`, arXiv:2402.08939). "LLMs are surprisingly brittle to the ordering of the premises, despite the fact that such ordering does not alter the underlying task… **permuting the premise order can cause a performance drop of over 30 %**." Best case: "when the premise order aligns with the context required in intermediate reasoning steps."
- **S20 — Sclar et al., ICLR 2024** (`peer-reviewed`, arXiv:2310.11324). "widely used open-source LLMs are extremely sensitive to subtle changes in prompt formatting in few-shot settings, with **performance differences of up to 76 accuracy points** when evaluated using LLaMA-2-13B"; recommends "reporting a range of performance across plausible prompt formats".
- **S21 — GSM-IC, ICML 2023** (`peer-reviewed`, arXiv:2302.00093). "the model performance is **dramatically decreased when irrelevant information is included**"; mitigations include "adding to the prompt an instruction that tells the language model to ignore the irrelevant information". Note the tension: the fix is another instruction, in a paper about instructions hurting.
- **S11 — Claude Code memory** (`official docs`). "**Structure**: use markdown headers and bullets to group related instructions. Claude scans structure the same way readers do: organized sections are easier to follow than dense paragraphs." "**Specificity**: write instructions that are concrete enough to verify. For example: 'Use 2-space indentation' instead of 'Format code properly'; 'Run npm test before committing' instead of 'Test your changes'."
- **S2** (`official docs`). "Structure longer reference files with table of contents"; "**Keep references one level deep**" — a *structural* position rule: the deeper the hop, the more likely a partial read ("Claude might use commands like `head -100` to preview content rather than reading entire files, resulting in incomplete information").

**Implication (my inference).** Hard constraints belong in the always-loaded trigger tier (frontmatter description / rules file loaded at launch) or at the top of the loaded body, never in the middle of a long body and never behind a second hop. This is consistent with, but not directly measured for, *instruction documents*; S18/S19 measure retrieved evidence and premises, not a rule's line position.

## D4. Rule conflicts and priority mechanisms

- **S22 — The Instruction Hierarchy, Wallace et al. 2024** (`preprint (arXiv)`, arXiv:2404.13208). "one of the primary vulnerabilities… is that **LLMs often consider system prompts… to be the same priority as text from untrusted users and third parties**"; the proposed hierarchy "explicitly defines how models should behave when instructions of different priorities conflict" and "teaches LLMs to **selectively ignore lower-privileged instructions**", using *context synthesis* (aligned) and *context ignorance* (misaligned) training data. Result claim: "drastically increases robustness… while imposing minimal degradations on standard capabilities."
- **S23 — OpenAI Model Spec, 2025-04-11** (`standard/spec`). "We assign each instruction in this document, as well as those from users and developers, a **level of authority**. **Instructions with higher authority override those with lower authority.**" Chain: Platform → Developer → User, where "**Platform: Rules that cannot be overridden by developers or users.**" Explicitly acknowledged as a *design* for conflict: "too broad to dictate specific actions in complex scenarios where the goals might conflict… This document aims to provide concrete instructions for navigating such conflicts."
- **Vendor precedence rules** ([S7] Cursor: "Team Rules → Project Rules → User Rules. All applicable rules are merged; **earlier sources take precedence when guidance conflicts**"; [S8] Copilot: personal > repository > organization, "all sets of relevant instructions are provided"; [S6] AGENTS.md: nearest file wins, chat overrides everything; [S9] dsh: numeric root ranks 100–600).
- **S11 — the failure admission** (`official docs`): "**Consistency**: if two rules contradict each other, **Claude may pick one arbitrarily**. Review your CLAUDE.md files, nested CLAUDE.md files in subdirectories, and `.claude/rules/` periodically to remove outdated or conflicting instructions." And the escalation path: "If the instruction is something that must run at a specific point, such as before every commit or after each file edit, **write it as a hook instead**. Hooks execute as shell commands at fixed lifecycle events and **apply regardless of what Claude decides to do**."
- **Mechanisms worth borrowing** ([S25] ESLint severity `"off"|"warn"|"error"` where warn "doesn't affect exit code" and is "typically used when introducing a new rule that will eventually be set to 'error'"; [S28] OPA `default` values and `else` chains — "Rules grouped together with the else keyword are evaluated until a match is found. Once a match is found, rule evaluation does not proceed to rules further in the chain", with hard failure on genuine ambiguity: "If a call matches multiple functions, they must produce the same output, or else a **conflict error** will occur"; [S29] AWS SCPs: "Any account has only those permissions permitted by every parent above it… effective permissions are the **logical intersection**").

**Measured conflict-resolution behaviour (honest answer).** The only quantitative conflict-resolution evidence I found is *training-time* [S22] (attack-success-rate reductions for GPT-3.5 trained on hierarchy data). I found **no published benchmark that measures how an instruction document's internal contradiction rate affects compliance**. The vendor-documented behaviour is qualitative: priority ordering is enforced by *ordering and liveness* (which file loads, which rule wins), and the model is explicitly documented as sometimes choosing arbitrarily [S11].

## D5. Self-modifying instructions: evidence and failure modes

**What works (with a metric and external feedback):**
- **S32 — APE: "Large Language Models Are Human-Level Prompt Engineers"** (`preprint (arXiv)`, arXiv:2211.01910). Treats the instruction as a program searched "in order to maximize a chosen score function"; "automatically generated instructions… achieve better or comparable performance to the instructions generated by human annotators on 19/24 tasks."
- **S33 — ProTeGi / Automatic Prompt Optimization, EMNLP 2023** (`peer-reviewed`, arXiv:2305.03495). Uses minibatch "natural language gradients" that "criticize the current prompt", then "edits the prompt in the opposite semantic direction of the gradient"; "improve an initial prompt's performance by **up to 31 %**".
- **S34 — DSPy** (`preprint (arXiv)`, arXiv:2310.03714). "We design a **compiler** that will optimize any DSPy pipeline to **maximize a given metric**"; compiled DSPy programs "are competitive with approaches that rely on expert-written prompt chains". Note the framing: the optimiser needs a metric before it can work.
- **S35 — Generative Agents** (`preprint (arXiv)`, arXiv:2304.03442 — id verified). The memory-stream architecture: agents "store a complete record of the agent's experiences using natural language, **synthesize those memories over time into higher-level reflections**, and retrieve them dynamically to plan behavior"; ablation shows "observation, planning, and reflection—each contribute critically to the believability of agent behavior". This is evidence that *write-then-summarise* memory works for believability; it is **not** evidence that summarisation preserves instruction fidelity.
- **S3** (`official docs`): Anthropic states the ambition to "enable agents to create, edit, and evaluate Skills on their own" — the vendor is moving toward self-authored instructions but has not published evidence for it.

**What fails:**
- **S37 — "Large Language Models Cannot Self-Correct Reasoning Yet", ICLR 2024** (`peer-reviewed`, arXiv:2310.01798). "**LLMs struggle to self-correct their responses without external feedback, and at times, their performance even degrades after self-correction.**" This is the central failure-mode citation: a model asked to "check whether a rule already exists" or "update your own instructions" is doing intrinsic self-correction, and the external metric that APE/APO/DSPy rely on is exactly what is missing.
- **S16** (`peer-reviewed`): instruction drift over 8 turns — self-authored memory written under a drifting instruction set inherits the drift.
- **S11** (`official docs`) — documented auto-memory failure modes, quoted from the troubleshooting list: "*I don't know what auto memory saved*"; "*My CLAUDE.md is too large*". The mechanism is capped: "The first **200 lines of MEMORY.md, or the first 25KB**, whichever comes first, are loaded at the start of every conversation. **Content beyond that threshold is not loaded at session start.**" And the write path fails *silently upward*: "If the file is over a limit, the write still succeeds, but Claude Code returns an error telling Claude to **rewrite the index**, because everything past the limit is **dropped on the next load**." The documented mitigation is that "Claude keeps MEMORY.md concise by moving detailed notes into separate topic files" plus an official trim tool: the `/doctor` checkup "cuts content Claude can derive from the codebase… and keeps pitfalls, rationale, and conventions that differ from tool defaults."
- **S9** (`local-file`): "**No body revision protocol** — a loaded body is ordinary retained tool history; later file edits affect later calls but **neither rewrite old results nor announce that the body changed**." For a self-editing skill this means an edit made mid-session does not retroactively correct already-loaded instructions, and nothing tells the model the rule changed.

**Documented failure-mode list (my synthesis, each tied to a source).** (1) *No metric* → self-correction degrades performance [S37]. (2) *Drift* → the instruction being edited is no longer the one that was loaded [S16]. (3) *Silent truncation* → over-limit self-written memory is dropped with no in-context signal [S11]. (4) *Stale loaded copy* → edited bodies do not revise what is already in context [S9]. (5) *Unverified growth* → nothing in any official format removes rules automatically; every vendor places that on a human review loop [S11, S7, S26].

## D6. Executable / verifiable rules vs prose advice

**Evidence that explicit checks help.**
- **S2** (`official docs`) makes the validator loop the recommended pattern: "**Common pattern:** Run validator → fix errors → repeat. **This pattern greatly improves output quality.**" Verifiable intermediates: "the 'plan-validate-execute' pattern… **Machine-verifiable:** Scripts provide objective verification"; "Make validation scripts verbose with specific error messages." Checklist pattern: "For particularly complex workflows, provide a checklist that Claude can copy into its response and check off as it progresses."
- **S38 — "Let's Verify Step by Step"** (`preprint (arXiv)`, arXiv:2305.20050). "**process supervision significantly outperforms outcome supervision** for training models to solve problems from the challenging MATH dataset", solving 78 %. **Caveat I must state plainly:** this is a *training/reward-model* result, not evidence that writing a "Verification:" line into a prompt improves compliance.
- **S40 — CheckList, ACL 2020** (`peer-reviewed`, arXiv:2005.04118, id verified). "a matrix of general linguistic capabilities and test types"; "NLP practitioners with CheckList created **twice as many tests, and found almost three times as many bugs** as users without it"; held-out accuracy "often overestimates the performance of NLP models".
- **S36 — Reflexion** (`preprint (arXiv)`, arXiv:2303.11366). "reinforce language agents **not by updating weights, but instead through linguistic feedback**"; agents "maintain their own reflective text in an episodic memory buffer"; "achieves a **91 % pass@1** accuracy on the HumanEval coding benchmark, surpassing the previous state-of-the-art GPT-4 that achieves 80 %". Reflexion's gains come with *external* feedback signals — consistent with [S37].
- **S44 — Microsoft Foundry built-in evaluators** (`official docs`, fetched by subagent). Ships a "**Task Adherence (preview)**" evaluator: "Measures whether the agent follows through on identified tasks according to **system instructions**", plus "a **Rubric** (preview): Scores a response or multi-turn conversation against custom, weighted criteria using an LLM as the judge."

**Counter-evidence — over-constraining and rigid templates.**
- **S10 — Anthropic, "Demystifying evals for AI agents"** (`official docs`/industrial report). "There is a common instinct to check that agents followed very specific steps like a sequence of tool calls in the right order. **We've found this approach too rigid and results in overly brittle tests**, as agents regularly find valid approaches that eval designers didn't anticipate. So as not to unnecessarily punish creativity, it's often better to **grade what the agent produced, not the path it took**." Grader trade-off table (per subagent report): code-based graders are "Brittle to valid variations that don't match expected patterns exactly"; model-based graders are "Non-deterministic… More expensive than code… Requires calibration with human graders for accuracy."
- **S2** (`official docs`) — "Set appropriate degrees of freedom": high freedom when "Multiple approaches are valid", low freedom only when "Operations are fragile and error-prone… A specific sequence must be followed."
- **S7** (`official docs`) — "**Avoid vague guidance**" cuts both ways: the same page forbids "instructions for edge cases that rarely apply" and says to "Use a linter instead" of copying style guides.
- **S21** (`peer-reviewed`) — extra text in context (irrelevant information) reduces accuracy "dramatically".
- **S39 — Ye & Durrett, NeurIPS 2022** (`peer-reviewed`, arXiv:2205.03401, id verified). "including explanations in the prompts… only yields **small to moderate** accuracy improvements", and "explanations generated by the LLMs **may not entail the models' predictions nor be factually grounded in the input**." Rationale-shaped prose does not reliably buy compliance.

**Verdict (my inference).** A *Verification* field pays for itself only when it names an artefact or command that a script or an external system can check; when it names a *thought* ("confirm you understood"), it converts into the same unreliable intrinsic self-check that [S37] measures as harmful. This is the strongest single constraint on R's V field.

## D7. Transferable mechanisms from requirements engineering, policy-as-code, linters, style guides

**(a) Requirements engineering — EARS** (`official docs`, author's own guide, S24). Structure: "**While <optional pre-condition>, when <optional trigger>, the <system name> shall <system response>**", with the ruleset "Zero or many preconditions; Zero or one trigger; One system name; One or many system responses." Five patterns, each a distinct *trigger class*: Ubiquitous (`The <system> shall <response>`), State-driven (`While…`), Event-driven (`When…`), Optional feature (`Where…`), Unwanted behaviour (`If…then…`), plus Complex combinations. Rationale: "System requirements are usually written in unconstrained natural language (NL), which is inherently imprecise… **EARS reduces or even eliminates common problems**", and "He found that requirements were easiest to read when **the clauses always appeared in the same order**." Adopters listed include Airbus, Bosch, Honeywell, Intel, NASA, Rolls-Royce, Siemens. (The page says "The notation was first published in 2009" but gives no full citation; the frequently-cited IEEE RE 2009 venue is **UNVERIFIED here**.)

**(b) Policy-as-code.** *OPA/Rego* (`official docs`, S28): `default` supplies a fallback when a rule body is undefined ("The `default` keyword allows policies to define a default value for documents produced by rules with complete definitions. The default value is used when all the rules sharing the same name are undefined"); `else` gives ordered, first-match-wins evaluation ("Rules grouped together with the `else` keyword are evaluated until a match is found. Once a match is found, rule evaluation does not proceed to rules further in the chain"); rules compose **additively** ("A rule may be defined multiple times with the same name… the rule definition is called *incremental* because each definition is additive"); negation is safety-constrained ("a variable appearing in a negated expression must also appear in another non-negated equality expression in the rule"); ambiguity in function dispatch is an **error, not a guess** ("they must produce the same output, or else a conflict error will occur"); and the canonical pattern is a `deny` set that carries a human-readable message: `deny contains $"User {input.username}'s role was '{role}', but must be one of {allowed_roles}" if { not role in allowed_roles }`. *AWS SCPs* (`official docs`, S29 + S55): **ceiling, not grant** — "an SCP never grants permissions. Instead, SCPs are access controls that specify the **maximum available permissions**"; blocking "either implicitly (by not being included in an Allow policy statement) or **explicitly** (by being included in a Deny policy statement)"; **deny-by-default with permission = intersection**: "For a permission to be allowed for a specific account, there must be an **explicit Allow statement at every level** from the root through each OU in the direct path to the account"; "SCP evaluation follows a **deny-by-default** model, meaning that any permissions not explicitly allowed in the SCPs are denied"; and deny is monotonic downward — "a deny policy at the root-level affects all accounts in the organization, **regardless of allow policies at lower levels**". AWS also documents a size limit that forces pruning.

**(c) Linter rule systems — ESLint, Semgrep, SonarQube** (`official docs`). *Severity* [S25]: `"off"|0`, `"warn"|1` ("doesn't affect exit code"), `"error"|2` ("exit code is 1 when triggered"), with the lifecycle use — warn is "typically used when introducing a new rule that will eventually be set to 'error'". *Precedence* [S25]: "When more than one configuration object specifies the same rule, the rule configuration is merged with the **later object taking precedence** over any previous objects." *Waivers instead of edits* [S25]: "Disabling ESLint rules inline should be **restricted and used only in situations with a clear and valid reason** for doing so", plus "Provide a comment explaining the reason for disabling a particular rule after the `--` section". *Per-rule metadata* [S48]: `type` is "one of **\"problem\", \"suggestion\", or \"layout\"**", where a *problem* "will cause an error or may cause a confusing behavior. Developers should consider this **a high priority to resolve**"; `fixable` is "Either \"code\" or \"whitespace\" if the `--fix` option … automatically fixes problems"; `hasSuggestions` marks human-applied fixes; `deprecated` is "(boolean | DeprecatedInfo)". *Machine-readable lifecycle* [S49]: "`deprecatedSince` … Semver of the version deprecating the rule", "`availableUntil` … Semver of the version likely to remove the rule", and "**The special value `null` means the rule will no longer be changed but will be kept available**" — plus a `replacedBy` pointer. *In the rules index* [S27]: every rule is tagged `✅ Recommended`, `🔧 Fixable`, `💡 hasSuggestions`, `❄️ Frozen` ("currently frozen and is not accepting feature requests"), and deprecated rules appear under "Deprecated… **deprecated in accordance with the deprecation policy, and replaced by newer rules**". *Deprecation policy* [S26]: "**Rules will never be removed from ESLint unless one of the following is true: The rule has been replaced by another core rule. A plugin exists with a functionally equivalent rule.** Rules will be deprecated as needed, **and marked as such in all documentation**. After a rule has been deprecated, the team will **no longer do any work on it**", and "You can continue to use deprecated rules **indefinitely** if they are working for you." *Graduation before freeze* [S50]: "Rules are considered **feature complete** when the intended purpose of the rule has been fully implemented such that it catches **80 % or more of expected violations and covers the majority of common exceptions**"; and after that, "We will **not** add any new options unless an option is the only way to fix a bug or support a newly-added ECMAScript feature" — residual edge cases are handled by waivers, not by rule growth. *Stable severity vocabulary across a rename* [S52, Semgrep]: "Severity can be LOW, MEDIUM, HIGH, or CRITICAL… The older levels ERROR, WARNING, and INFO match HIGH, MEDIUM, and LOW. **Severity values remain backwards compatible.**" *Rule type × status* [S53, SonarQube]: "There are four types of rules: Code smell (maintainability domain) Bug (reliability domain) Vulnerability (security domain) Security hotspot (security domain)"; and "rules can have 3 different statuses: Beta… **Deprecated: The rule should no longer be used because a similar, but more powerful and accurate rule exists**. Ready: The rule is ready to be used in production." SonarQube also attaches "coding attributes: consistency, intentionality, adaptability, responsibility".

**(d) Style guides.** *Rust API Guidelines* (`official docs`, S30): a stable `C-*` identifier per guideline, grouped into 11 thematic categories whose headers carry a scope definition ("`**Documentation** *(crate is abundantly documented)* — [ ] Crate level docs are thorough and include examples ([C-CRATE-DOC])`"), with a "**concise checklist of all individual guidelines, suitable for quick scanning during crate reviews**" alongside explanatory chapters; and an explicit strength disclaimer — "These are only guidelines, **some more firm than others**. In some cases they are vague and still in development… **should not in any way be considered a mandate**." **Negative finding:** a machine-readable *strength/priority* tag vocabulary does **not** exist in this guideline set — checked `about`, `README`, `checklist`, and the category sources; the only strength statement is "some more firm than others" [S47-subagent report]. *Google Style Guides* (`official docs`, S31): "Every major open-source project has its own style guide: a set of conventions (**sometimes arbitrary**) about how to write code for that project", with a single authoritative change channel — "Changes to the style guides are made to the **internal style guides first** and eventually copied into the versions found here. **External contributions are not accepted.**" *Google eng-practices* (`official docs`, S54) supplies two precedence devices: an ordering — "On matters of style, **the style guide is the absolute authority**. Any purely style point… that is not in the style guide is a matter of personal preference" — and an explicit **non-blocking severity class** for advisory rules: "if it's not very important, prefix it with something like **\"Nit: \"** to let the author know that it's just a point of polish that they could choose to ignore."

**Transferable set (my inference, ranked by evidence strength).** (1) *Typed trigger clauses* [S24, S7, S8] — strongest. (2) *Explicit default + ordered override + hard error on ambiguity* [S28, S29, S55, S23] — strong, and the error-on-ambiguity behaviour is what prose rules lack. (3) *Severity as a first-class field* [S25] — strong, one token; Semgrep proves the vocabulary can be renamed without breaking users [S52]. (4) *Rule status + replacement pointer* [S27, S26, S49, S53] — strong, and it makes deletion safe. (5) *Waivers instead of rule edits* [S25] — strong: a reasoned, reviewable inline exception is cheaper than a new rule option, and ESLint's freeze rule depends on it [S50]. (6) *A written graduation threshold before freeze* [S50] — moderate (80 %-of-expected-violations is an ESLint-specific number, but the *pattern* is portable). (7) *Stable rule ids + a scannable checklist view* [S30] — moderate; ids are what make "which rule fired?" answerable. (8) *Explicit precedence ordering + a non-blocking advisory class* [S54] — moderate; the "Nit:" class is exactly what a `warn` severity encodes. (9) *Explicit strength disclaimer* [S30, S2] — moderate; prevents a soft guideline being read as a hard constraint. **Not evidenced (do not borrow):** a machine-readable strength tag in Rust's guidelines, an OPA/Rego versioning policy, and the ISO/IEC/IEEE 29148 quality-characteristic wording — all three were searched for and not found [S56 notes].

## D8. Rule lifecycle: deprecation, priority, avoiding rule rot

- **Written removal precondition** [S26] — the single strongest anti-rot mechanism found. A rule may be removed only if a replacement exists (core rule or plugin equivalent); deprecation is documented per rule; deprecation ends maintenance.
- **Status taxonomy on every rule** [S27] — recommended / fixable / suggestion / frozen / deprecated, surfaced in the rule index. "Frozen" is the missing middle state most agent rule-sets lack: *kept, but not accepting changes*.
- **Warn-then-error graduation** [S25] — new rules enter at `warn` and are promoted to `error` once trusted. This is a cheap, official lifecycle for a new rule whose false-positive rate is unknown, and it maps directly onto an agent skill's rule set.
- **A written graduation threshold, then freeze** [S50] — ESLint declares a rule "feature complete" at "**80 % or more of expected violations and covers the majority of common exceptions**", after which "We will **not** add any new options unless an option is the only way to fix a bug". The portable part is the *policy shape*: state a coverage bar, then stop accepting new clauses and route edge cases to waivers. This is the strongest available answer to "how do I stop a rule set growing".
- **Machine-readable lifecycle metadata instead of prose notes** [S49] — `deprecatedSince` (semver), `availableUntil` (semver or `null`, where "**null means the rule will no longer be changed but will be kept available**"), and a replacement pointer. Three fields turn "is this rule still alive?" into a query rather than a judgement call. SonarQube's Beta/Ready/Deprecated triplet [S53] is the same idea with coarser granularity.
- **Severity changes ride major versions** [S51] — ESLint's release policy keeps breaking rule changes out of minor releases ("Regular releases that follow semantic versioning and are considered production-ready. Prereleases… intended to give the community a preview"), which is what lets a team adopt new rules on a schedule.
- **Waivers instead of local rule edits** [S25] — "Disabling ESLint rules inline should be **restricted and used only in situations with a clear and valid reason**", and the reason must be written in the comment. Applied to a skill: an exception belongs next to the case that needs it, with its justification, not as a new clause in the shared rule.
- **Deny-only rule sets age better than allow-lists** [S55] — AWS documents "a **deny list** SCP that prohibits access to three AWS services. All services that aren't listed in the SCP's Deny statement are allowed", and deny is monotonic ("a deny policy at the root-level affects all accounts… regardless of allow policies at lower levels"). A short prohibition list stays correct as the world grows; an exhaustive allow-list rots by omission.
- **A single authoritative change channel** [S31] — "Changes to the style guides are made to the **internal style guides first** and eventually copied into the versions found here. External contributions are not accepted." One place to edit is what makes "no rule rot" checkable at all.
- **Baseline-and-trim tooling** [S11] — Claude Code's `/doctor` "proposes trims for a checked-in CLAUDE.md: it **cuts content Claude can derive from the codebase**, such as directory layouts, dependency lists, and architecture overviews, and **keeps pitfalls, rationale, and conventions that differ from tool defaults**", gated on a version requirement. This is a concrete, official de-rot procedure: delete what the environment already encodes, keep the non-derivable.
- **Growth policy that resists accumulation** [S7] — "**Start simple. Add rules only when you notice Agent making the same mistake repeatedly.**" Plus the four documented anti-patterns (copying style guides, documenting every command, rare edge cases, duplicating the codebase) [S7].
- **Single-source-of-truth + pointer instead of copy** [S7] — "Reference files instead of copying their contents… **prevents them from becoming stale** as code changes."
- **Human review cadence for contradictions** [S11] — "Review your CLAUDE.md files, nested CLAUDE.md files in subdirectories, and `.claude/rules/` **periodically to remove outdated or conflicting instructions**", motivated by the arbitrary-choice failure mode.
- **Load-order discipline** [S11] — `.claude/rules/` split by topic ("Each file should cover one topic, with a descriptive filename like `testing.md`"), path-scoped so instructions "only load into context when Claude works with matching files, reducing noise and saving context space"; rules without `paths` "are loaded at launch with the same priority as `.claude/CLAUDE.md`". Note the deliberate division of labour: "For task-specific instructions that don't need to be in context all the time, use skills instead."
- **Aging/obsolescence at the format level** [S2] — "Avoid time-sensitive information", and when it must stay, move it under an "Old patterns" heading inside `<details>`.

**Evidence about rule sets *decaying*.** I found **no quantitative study** measuring rule-set decay over time in agent instructions. The closest hard facts are structural: silent truncation past the load cap drops content with no in-context signal [S11]; malformed frontmatter silently removes a whole skill with no model-visible diagnostic [S9]; contradictory rules are resolved arbitrarily [S11]; and instruction drift erodes compliance over a session independent of edits [S16]. Decay is therefore *documented as mechanism*, not measured as a rate.

## D9. How to TEST an instruction document's behavioural effect (methods + limits)

**Vendor-prescribed methods.**
- **S2** (`official docs`) — the Skill-specific method, and the only one written for *instruction documents*: "Build evaluations first: **Create evaluations BEFORE writing extensive documentation**", with a JSON shape `{skills, query, files, expected_behavior[]}`, "three scenarios", baseline-without-skill, then "Write minimal instructions… Iterate: Execute evaluations, compare against baseline". Anthropic is explicit that tooling is absent: "**There is not currently a built-in way to run these evaluations.** Users can create their own evaluation system."
- **S10** (`official docs`/industrial report) — the best official methodology located. "In reality, **20-50 simple tasks drawn from real failures is a great start**… this large effect size means small sample sizes suffice"; "Because model outputs vary between runs, we run **multiple trials**"; **regression vs capability evals**: capability evals "should start at a low pass rate", regression evals "should have a **nearly 100 % pass rate**"; "Ambiguity in task specifications becomes noise in metrics. The same applies to criteria for model-based graders: **vague rubrics produce inconsistent judgments**"; "LLM-as-judge graders should be **closely calibrated with human experts**"; "Like the **Swiss Cheese Model**… no single evaluation layer catches every issue"; and the design warning "grade what the agent produced, not the path it took".
- **S43 — OpenAI "Working with evals"** (`official docs`, subagent-fetched). Frames eval design as "somewhat similar to **behavior-driven development (BDD)**, where you begin by specifying how the system should behave before implementing and testing the system." **Status note:** the page states "**OpenAI is deprecating the Evals platform**… read-only for existing users on October 31, 2026, and the platform is scheduled to shut down on November 30, 2026." The open-source `openai/evals` README adds: "a good eval will inevitably require **careful thought and rigorous experimentation**."
- **S45 — promptfoo** (`official docs`, tool, subagent-fetched). Assertion semantics and a documented trap: "**Common issue: Tests show PASS even when scores are low**"; "a result like `{"pass": true, "score": 0}` will pass without a threshold, but fail with `threshold: 1`". CI integration: "Catch regressions early", "Enforce minimum performance thresholds".

**Statistical validity.**
- **S42 — "Adding Error Bars to Evals"** (`preprint (arXiv)`, arXiv:2411.00640, id verified). "**Fundamentally, evaluations are experiments**; but the literature on evaluations has largely ignored the literature from other sciences on experiment analysis and planning." Its abstract gives **no concrete sample-size number** — a specific "you need N samples" figure is **NOT FOUND** in the abstract (full PDF not retrieved).
- **S20** (`peer-reviewed`) — up to 76 accuracy points from formatting alone; therefore a single-format A/B of an instruction document cannot separate the document's effect from its formatting.
- **S41 — MT-Bench / LLM-as-a-judge, NeurIPS 2023 D&B** (`peer-reviewed`, arXiv:2306.05685, id verified). "We examine the usage and limitations of LLM-as-a-judge, including **position, verbosity, and self-enhancement biases**, as well as limited reasoning ability"; ceiling claim: GPT-4 judges match human preferences "achieving **over 80 % agreement**, the same level of agreement between humans."
- **S46 — Hamel Husain, "Your AI Product Needs Evals"** (`practitioner opinion`, subagent-fetched). "To know whether your AI product is working, you need a way to measure success **beyond vibe checks**"; three levels (unit-test assertions → human+model eval on traces → A/B), "The cost of Level 3 > Level 2 > Level 1"; judge-validity discipline: "You should **track the correlation between model-based and human evaluation** to decide how much you can rely on automatic evaluation", and raw agreement "can be misleading when classes are imbalanced. Instead, you should typically measure **precision and recall separately**"; threshold discipline: "unlike traditional unit tests, you don't necessarily need a 100 % pass rate. Your pass rate is a product decision"; and the irreducible cost: "**You can never stop looking at data—no free lunch exists.**"
- **S40** (`peer-reviewed`) — method transfer: capability × test-type matrices beat held-out accuracy, which "often overestimates" behaviour. Adapted to an instruction document: build a matrix of *rule × scenario class* rather than one aggregate score.

**What practitioners actually do, and its limits (my synthesis).** (1) Write 3–50 tasks drawn from *observed failures*, not imagined ones [S2, S10, S46]. (2) Run the document against a baseline without it, multiple trials [S2, S10]. (3) Prefer deterministic assertions; where impossible, use a calibrated LLM judge and track judge–human correlation [S45, S41, S46, S10]. (4) Keep a regression suite at ~100 % and separate capability probes at low pass rates [S10]. Limits: no deterministic test exists for a prose instruction; judge scores carry position/verbosity/self-enhancement bias and ~80 % agreement is the ceiling [S41]; a "pass" can be reported with score 0 unless a threshold is set [S45]; formatting alone can swamp the effect [S20]; and sample-size power requires statistics no vendor doc currently supplies [S42].

## D10. Assessment of the proposed R = (T, C, A, K, V, E) schema

**Does the evidence support it?** Partially. Five of six fields map onto mechanisms that mature systems actually ship; one (C) has no counterpart anywhere in the sources. Field-by-field:

| field | verdict | evidence | token cost per rule (est.) |
|---|---|---|---|
| **T Trigger** | **Keep — strongest field.** Every format triggers on a string/glob; EARS' five patterns are trigger classes | [S1,S5,S7,S8,S9,S24] | 8–20 (as a frontmatter fragment) |
| **C Context** | **Drop.** No format has it; it duplicates T or the enclosing section | none found | 10–25 wasted |
| **A Action** | **Keep**, but only if concrete and checkable | [S11 "concrete enough to verify", S7 "avoid vague guidance", S2 degrees-of-freedom] | 15–30 |
| **K Constraint** | **Demote to a severity tag.** The *count* of constraints is the measured failure axis; a separate prose field adds tokens without adding enforcement | [S13 ceiling ~3, S25 off/warn/error, S29 explicit deny, S23 authority levels] | 10–25 saved |
| **V Verification** | **Keep, conditionally** — only when it names a script/command/artefact | [S2 validator loop + "machine-verifiable", S38, S37, S11 hooks] | 10–30 |
| **E Exception** | **Keep, but fold into T** (narrow the trigger rather than caveat the action) | [S24 Where/If-then as trigger classes, S28 else/default, S29 intersection, S25 per-file overrides] | 8–20 |

**Which fields earn their keep.** T, A, V. T is the field that makes a large rule set *survivable at all*: FollowBench's ~3-constraint ceiling is measured **per instruction**, i.e. per simultaneously-active constraint set [S13], while progressive disclosure keeps most of a skill's text idle and unloaded [S1,S3]. A 60-rule document with mutually exclusive triggers presents ~3–5 live rules per task — which is the only structural reason a rule set can exceed the measured ceiling. That is my inference, but it is the inference the whole format design rests on.

**What is ceremony.** C, and K-as-prose. C is unfalsifiable in review (nobody can say whether a rule's "Context" is wrong) and duplicates T. K-as-prose is a *negation* in disguise: stating a prohibition puts the forbidden action in context, and the closest measured evidence is the distractibility result [S21]; the positive-action formulation is also what Anthropic recommends ("State what to do rather than narrating how or why" [S5]). **Honest caveat:** I found no peer-reviewed citation for the specific claim that prohibitions harm agent instruction-following; the "state the positive" rule appears in the local practitioner reference [S47] and in vendor phrasing [S5], so treat it as **practitioner guidance, not a research finding**.

**Token cost per rule.** Grounded figures: a concise worked example ≈50 tokens vs a verbose one ≈150 tokens for the same content [S2]; Level-2 body budget "Under 5k tokens" [S1] and "under 500 lines" [S2]; always-loaded pointer ≈100 tokens per skill [S1]; Claude Code target "under 200 lines" for CLAUDE.md [S11]; auto-memory loads only "the first 200 lines… or the first 25KB" [S11]. A full six-field rule runs **≈70–150 tokens**; a three-field rule (T, A, V) runs **≈35–80**. At ~13 tokens/line, a 500-line body holds roughly **40–90** full-field rules or **80–180** three-field rules — but the 5k-token Level-2 cap bites first, at roughly **33–70** full-field rules. The always-loaded tier is far tighter: 200 lines ≈ **15–25** short rules.

**Observed practice in a working corpus** ([S47], `local-file`; method: enumerate every `SKILL.md` under the skills root, count lines and frontmatter keys). 25 skills, **median 71 lines**, max 140, **none over 500**; total 1,591 lines; **22** sibling reference files (max 207 lines, e.g. `triage/AGENT-BRIEF.md`), i.e. detail is disclosed one hop down; **11 of 25** use a model-invoked `description` containing "Use when", and none use a `Context`-like field. This is sample evidence that a mature practitioner corpus converges on *short bodies + one-hop disclosure*, which is what the official guidance asks for [S1,S2].

**Concrete recommendation.**

1. **Reduce to `R = (T, A, V)` per rule, plus two document-level fields: `severity` and `status`.**
   - `T` — a typed trigger clause, EARS-style: `When <event>` / `While <state>` / `Where <feature>` / default/ubiquitous [S24]. This is where the Exception goes: an exception is a *narrower trigger*, not a caveat.
   - `A` — one concrete, checkable action [S11].
   - `V` — either a real command/artefact check, or the explicit marker `V: none`. **Require the marker**, so an unverifiable rule is visibly unverifiable rather than silently soft [S2, S37].
   - `severity` — `error | warn | off`, borrowed from ESLint, with the graduation rule: new rules enter at `warn` [S25].
   - `status` — `candidate | active | frozen | deprecated`, with a mandatory `replaced-by` when deprecated and, borrowing ESLint, a date/semver field so "is this still alive?" is a lookup rather than a judgement [S27, S26, S49, S53].
   - **Exceptions are waivers, not clauses.** Where a rule genuinely cannot apply, record a local, reasoned waiver next to the case (ESLint's inline-disable discipline: "restricted and used only in situations with a clear and valid reason") rather than widening the shared rule [S25]. Once a rule set stabilises, declare a coverage bar and **stop adding clauses** [S50].
2. **Budget explicitly, and enforce it in review**: frontmatter pointer ≤ the format cap (1,024 chars [S1]; note Claude Code truncates description+when_to_use at 1,536 chars [S5]); body ≤ 200 lines (≈2,600 tokens) unless the skill is user-invoked; ≤ one hop of reference; target ≤ 5 *simultaneously live* rules per trigger branch, because that is where measured compliance is still ≈70–85 % [S13].
3. **Cost and failure modes of this recommendation.** Dropping C removes a place to record *why* a rule exists; the mitigation is a document-level "Rationale" section, not a per-rule field (this is also what `/doctor` protects: "keeps pitfalls, **rationale**, and conventions that differ from tool defaults" [S11]). Folding E into T can hide an exception inside an over-narrow trigger, making a rule never fire; the mitigation is a review question — "which branch reaches this rule?" — and, in a real system, a counter per rule. Adding `status` costs one token per rule but introduces a new failure: a `deprecated` rule left loaded still consumes attention, so deprecation must mean *removal from the loaded document*, with the pointer kept in an "Old patterns" section [S2].
4. **What the evidence does *not* support.** No source justifies six mandatory fields per rule, and no source measures the compliance benefit of structured fields over prose. **A rule schema's real value is *reviewability* (a human or agent can check each field) and *budgeting* (fields make token cost visible), not a measured compliance gain.** Stated plainly: the schema is a design judgement supported by analogue mechanisms from other fields, not by an experiment on agent instruction-following.

## D13. Limitations / unverified

- **Tooling outage.** `web_fetch`, `web_search` and `anysearch_search` failed all session with HTTP 402 from the upstream extract service; Windows TLS is sandbox-blocked for `curl.exe`/`Invoke-WebRequest`. Node `fetch` was the only working path. Consequence: **no search-engine discovery was possible**, so sources were reached by direct URL, by URLs found inside fetched pages, or by prior knowledge of the arXiv id — every id cited was then verified by fetching its abs page and matching title/authors.
- **Anthropic prompt-engineering docs are geo-blocked**, not 404: `docs.claude.com/.../test-and-evaluate/*` and `platform.claude.com/docs/en/test-and-evaluate/*` return HTTP 200 with a 7,246-byte interstitial reading "App unavailable in region… Claude is only available in certain regions right now." Verified by a delegated subagent. **Their content is therefore unretrieved**; the Agent Skills pages [S1,S2] succeeded because they were fetched before the outage through a different egress.
- **UNVERIFIED and excluded from the argument:** the claim of a "~60–100 lines before degradation begins" CLAUDE.md instruction-following ceiling, attributed to `claude-wiki.com` in one search snippet. I did not fetch the page, it shows no provenance, and no official or peer-reviewed source states such a threshold. **Do not use that number.** The defensible numbers are FollowBench's CSL ≈ 3 constraints per instruction [S13], 200 lines for CLAUDE.md [S11], and 500 lines / 5k tokens for SKILL.md [S2,S1].
- **"Instruction-following ceiling" as a term** appears to be practitioner vocabulary, not a defined quantity in the literature I reached. No published curve of *system-prompt length* vs compliance was found. That is a negative finding, not a gap I filled by inference.
- **Transfer inferences I flag as inference, not evidence:** (a) that FollowBench's per-instruction constraint ceiling bounds a *document's* rule count only through trigger-gating; (b) that primacy/recency from [S18,S19] applies to the *position of a rule within a document*; (c) that ESLint/OPA/SCP mechanisms improve agent compliance — those are analogues from systems with deterministic evaluators. None of these is measured for agent instruction documents.
- **Quotes fetched by a delegated subagent, not by me:** S20, S39–S46. The subagent reported HTTP 200 plus verbatim quotes and independently re-verified five arXiv ids (2306.05685, 2005.04118, 2205.03401, 2310.11324, 2411.00640) against title and authors; it also reported that promptfoo's "regression testing" page is a genuine 404 (corroborated by scanning the site's 553-URL sitemap) and that OpenAI's evals page contains **no** model-graded caveat sentence. The MT-Bench/CheckList figures are as quoted; I did not re-fetch those two pages myself.
- **Local corpus method and its limits** [S47]: counted with `Get-ChildItem -Recurse -Filter SKILL.md` under the skills root — **25** files (not 27), median 71 lines, max 140, total 1,591 lines, 22 sibling `.md` files. A `project-conventions` skill appeared in the session catalog mid-task but **no such directory existed on disk** at that path when I searched, so its content is unread and uncounted. "Uses 'Use when'" was detected by substring match on the frontmatter `description` line only; multi-line YAML descriptions would be undercounted.
- **Not attempted / not found:** InFoBench's per-count DRFR curve (abstract only); IFEval's per-count breakdown beyond totals (Figure 2 is an image); the full text of "Adding Error Bars to Evals" (no sample-size number in the abstract); any peer-reviewed study of *rule-set decay over time* in agent instructions (none found — D8's decay claims are mechanism-level, not measured); any official Anthropic prompt-engineering page on placement/ordering; a semantic-versioning policy specific to rule sets (Crossref/registry lookups were not reachable for this).
